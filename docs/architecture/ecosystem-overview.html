מסמך זה הוא נקודת הכניסה לתיעוד של מערכת הפלאגינים. הוא מסביר כיצד הפלאגינים שלנו משתפים ידע על מאגר הקוד: פלאגין אחד גוזר את הידע פעם אחת ומאשר אותו מול מפתח, וכל שאר הפלאגינים מפנים אליו במקום לגזור אותו מחדש.

01

The plugin ecosystem

Four plugins are distributed through one internal marketplace, ono-plugin-marketplace. A developer adds the marketplace once and installs any of them from a single catalogue, over HTTPS, with no SSH keys required.

Project Inspector Producer

Reads an existing repository and gradually builds an approved knowledge base about it — project context, an audit topic index, a descriptive knowledge base, and one reviewed audit document per topic. It never modifies source code.

Mobile Dev Plugin Consumer

An eight-stage feature pipeline across React Native, native iOS, native Android and React web, with a human approval gate between every stage. It consumes the Inspector's knowledge rather than re-deriving it.

QA Plugin

Authors test plans from designs and specifications, in parallel with development, then compares them against the dev team's handoff notes to surface untested edge cases.

Spec Team Toolkit

Builds the customer-facing High Level Design and the developer-facing Low Level Design that feed both the dev and QA pipelines.

The two documented in depth here are the Inspector and the Mobile Dev Plugin, because they are the pair joined by the Repository Knowledge contract. The QA plugin and the Spec toolkit participate in the same feature lifecycle but do not yet consume that contract.

עברית · מערכת הפלאגינים

ארבעה פלאגינים מופצים דרך מרקטפלייס פנימי אחד. המפתח מוסיף את המרקטפלייס פעם אחת ומתקין מתוכו כל פלאגין, דרך HTTPS וללא צורך במפתחות SSH.

  • Project Inspector — קורא מאגר קוד קיים ובונה עליו בסיס ידע מאושר. אינו משנה קוד מקור אף פעם.
  • Mobile Dev Plugin — צינור פיתוח בן שמונה שלבים, עם שער אישור אנושי בין כל שני שלבים. צורך את הידע של ה־Inspector במקום לגזור אותו מחדש.
  • QA Plugin — כותב תוכניות בדיקה במקביל לפיתוח ומשווה אותן למסמכי המסירה.
  • Spec Team Toolkit — בונה מסמכי HLD ו־LLD שמזינים את שני הצינורות.

שני הראשונים מתועדים כאן בהרחבה, מפני שהם הזוג שמחובר בחוזה ה־Repository Knowledge.

02

Why Repository Knowledge exists

Each plugin used to work out what the repository was, independently, every time it ran. The same facts — which navigation library, which state manager, where the modules live, which screens already exist — were derived up to five times, in different vocabularies, with nothing reconciling them.

The cost was not wasted effort. It was three concrete failures:

An unread inventory

The component inventory exists specifically so a feature can reuse what already exists. Nothing in the dev plugin read it, so the architect proposed new components without ever seeing the list of existing ones.

Findings that never arrived

Audit findings a human had reviewed and approved were invisible to code review. They were re-discovered, re-worded, or quietly contradicted.

Facts frozen into documents

Every feature analysis pasted in a snapshot of repository conventions. After the next refactor that snapshot was wrong — while three later stages were told to trust it.

Before

Re-derived
  • ✕Knowledge derived 2–5 times, never reconciled
  • ✕Full stack inventory re-scanned on every command
  • ✕Approved documentation existed but nothing read it
  • ✕Documents embedded verbatim snapshots that went stale silently
  • ✕No way to tell whether a document's repository facts were still true

After

Derived once
  • ✓Derived once, human-approved, published as a contract
  • ✓Reused when covered; only genuine gaps derived live
  • ✓Approved documentation is the source every stage reads
  • ✓Documents carry citations — path, section, fingerprint
  • ✓Staleness detected per document and reported, never guessed around
עברית · למה זה קיים

בעבר כל פלאגין גזר בעצמו את הידע על המאגר, בכל הרצה מחדש. אותן עובדות נגזרו עד חמש פעמים, באוצר מילים שונה, בלי שדבר יאחד ביניהן. המחיר לא היה בזבוז זמן אלא שלוש תקלות ממשיות:

  • מלאי רכיבים שלא נקרא — קיים מסמך שמפרט מה כבר בנוי, כדי שפיצ'ר חדש יעשה בו שימוש חוזר. אף רכיב בפלאגין הפיתוח לא קרא אותו.
  • ממצאים שלא הגיעו ליעדם — ממצאי אודיט שאדם בדק ואישר לא היו נראים בסקירת הקוד, ולכן גולו מחדש או אף נסתרו.
  • עובדות שהוקפאו לתוך מסמכים — כל ניתוח פיצ'ר הדביק בתוכו תצלום־רגע של מוסכמות המאגר. אחרי הריפקטור הבא הוא היה שגוי, ושלושה שלבים אחריו הונחו לסמוך עליו.

אחרי השינוי: הידע נגזר פעם אחת, מאושר בידי אדם, ומפורסם כחוזה. מסמכים מפנים אליו במקום להעתיק אותו, ואי־עדכניות מזוהה ומדווחת ברמת המסמך הבודד.

03

How the plugins cooperate

One question each. The Inspector answers what is this repository? The Dev Plugin answers what are we changing, and how? Nothing flows back upward: the Inspector never reads a feature document, and no consumer ever writes an Inspector-owned artifact.

Project Inspector Producer

Owns: what the repository is

Responsibilities

  • Derive repository knowledge once, under human approval
  • Identity, stack, build and test commands
  • Structure, module map, entry points
  • Component inventory and coding conventions
  • Integrations and environment variable names
  • Audit topic index and its approval state

Produces

  • CLAUDE.md — compact project context
  • AUDIT.md — audit topic index
  • docs/project/ — overview, components, patterns, integrations
  • audits/ — one reviewed document per topic
  • .ono/repo-knowledge.json — the derived index

Never

  • Modifies source code
  • Reads a feature document
  • Decides anything about a feature

Mobile Dev Plugin Consumer

Owns: what we are changing

Responsibilities

  • Decide platform and device type per feature, with a human
  • The design reference for a feature
  • Technical approach and design document
  • Task decomposition and implementation
  • Reviews and per-diff file attribution
  • Judging the repository against our architecture standards

Consumes

  • .ono/repo-knowledge.json — through one component only
  • docs/project/patterns.md — conventions, cited by section
  • docs/project/components.md — inventory, read before proposing anything new
  • docs/project/integrations.md — services and SDKs
  • CLAUDE.md — structure, via fixed pointers

Never

  • Writes an Inspector-owned artifact
  • Treats the manifest's platform hints as authoritative
  • Resolves device type from the manifest
  • Repairs stale knowledge — it reports and recommends a refresh

The boundary that matters most

It is not producer-versus-consumer. It is observations versus decisions. What the repository is can be derived once and shared. What we have decided about a feature — which platform, which device type — belongs to the moment a human confirmed it, and must never be inferred from shared data. The manifest deliberately has no single authoritative platform field, so it cannot be misread as one.

עברית · חלוקת האחריות

שאלה אחת לכל פלאגין. ה־Inspector עונה על מה המאגר הזה; פלאגין הפיתוח עונה על מה אנחנו משנים וכיצד. הזרימה חד־כיוונית: ה־Inspector אינו קורא מסמכי פיצ'ר, וצרכן אינו כותב לעולם לארטיפקט שבבעלות ה־Inspector.

הגבול החשוב באמת אינו יצרן־מול־צרכן אלא תצפיות מול החלטות. מה שהמאגר הוא ניתן לגזירה פעם אחת ולשיתוף. מה שהוחלט על פיצ'ר — איזו פלטפורמה, איזה סוג מכשיר — שייך לרגע שבו אדם אישר זאת, ואסור להסיק אותו מנתונים משותפים. לכן ה־manifest אינו מכיל שדה פלטפורמה מחייב אחד, כדי שלא ייקרא בטעות ככזה.

04

Repository Knowledge, stage by stage

Knowledge is produced at the top and consumed below. Steel-edged stages belong to the Inspector; green-edged stages belong to the Dev Plugin.

01

Project scan

Project Inspector · /inspect

Reads the repository once, with a human approval gate at every stage. Produces the baseline context and the audit topic index. Nothing is automatic or silent.

02

Approved repository documentation

Project Inspector · reviewed artifacts

CLAUDE.md, AUDIT.md and the docs/project/ knowledge base. A person reviewed each one. These remain the source of truth; nothing downstream replaces them.

03

repo-knowledge.json

Project Inspector · derived index

A machine-readable index over those documents — never a second copy. It holds paths and section anchors, a fingerprint (commit plus per-document hash), and a per-category coverage rating of populated, partial or unknown. It reads no source code, so the review that approved the documents also covers this.

04

/analyze-feature → Feature Analysis

Mobile Dev Plugin

Resolves the manifest before detecting anything, reuses what it covers, derives the rest live, then asks a human to confirm exactly one platform and one device type. The analysis records the confirmed decisions and cites knowledge by path, section and fingerprint.

05

/dev-design-start → Design Document

Mobile Dev Plugin

Re-resolves knowledge at design time, because the repository may have moved since the analysis was approved. Reads the approved documents first and inspects source only for what they cannot contain — the actual signatures and call sites of the components this feature touches.

06

/dev-feature-start → Task Breakdown

Mobile Dev Plugin

Decomposes the approved design into individually reviewable, testable and revertible tasks, each carrying the feature's single confirmed platform.

07

/implement-task → Implementation

Mobile Dev Plugin

Implements exactly one task, resolving the whole approved chain from document links rather than guessing filenames.

עברית · צינור הידע

הידע נוצר למעלה ונצרך למטה. שלבים בקו כחול שייכים ל־Inspector; שלבים בקו ירוק שייכים לפלאגין הפיתוח.

  • סריקת הפרויקט — קריאה אחת של המאגר, עם שער אישור אנושי בכל שלב.
  • תיעוד מאושר — CLAUDE.md, AUDIT.md ובסיס הידע התיאורי. אדם בדק כל אחד מהם, והם נשארים מקור האמת.
  • קובץ ה־manifest — אינדקס קריא־למכונה מעל אותם מסמכים, ולא העתק שני שלהם. מכיל נתיבים, עוגני־מקטע, חתימת רעננות ודירוג כיסוי לכל קטגוריה.
  • ניתוח הפיצ'ר — פותר את ה־manifest לפני כל זיהוי, ומבקש מאדם לאשר פלטפורמה אחת וסוג מכשיר אחד. הניתוח מצטט ידע ואינו מעתיק אותו.
  • מסמך העיצוב — פותר את הידע מחדש, כי המאגר עשוי להיות שונה מאז שהניתוח אושר. קורא קוד מקור רק למה שהמסמכים אינם יכולים להכיל.
  • פירוק למשימות ומימוש — משימות בדידות שניתן לסקור, לבדוק ולבטל כל אחת בנפרד, ולאחריהן מימוש של משימה אחת בכל פעם.

05

What the manifest holds — and deliberately does not

CategoryBacked byUsed for
stackCLAUDE.mdLanguages, frameworks, tooling, package managers
commandsCLAUDE.mdInstall, run, test, build
structureCLAUDE.mdRepository tree, key modules, entry points
inventorydocs/project/components.mdExisting screens, components, hooks — reuse before creating
conventionsdocs/project/patterns.mdState, API, navigation, styling, errors, i18n, naming, testing
integrationsdocs/project/integrations.mdServices, SDKs, environment variable names
auditTopicsAUDIT.mdWhich topics exist and their approval status

Deliberately excluded

Audit findings

Only the topic index is carried — never a finding's body. Feeding approved findings into code review is a separate, larger piece of work.

Platform authority

Advisory hints only. There is no single authoritative platform field, because platform is a human decision per feature.

Device information

Nothing at all. Mobile-versus-TV is resolved live for every feature.

Task lifecycle state

Out of scope. The manifest describes the repository, not the work in flight.

Freshness, and honest degradation

The manifest records the commit it was built from and a hash per source document. A consumer compares both, producing one of four verdicts, evaluated in this order:

VerdictMeaningConsumer behaviour
stale-artifactsA source document changedDerive the affected categories live; keep the rest
unknownFreshness could not be establishedUse as-is, report that
stale-headCommit moved, documents unchangedUse as-is, note how far behind
freshEverything matchesTrust every covered category

Staleness is attributed per document, so editing one approved file demotes only the category it backs. And a category that cannot be determined is reported unknown rather than guessed — failure degrades to no better than before, never to wrong.

The property everything else rests on

The manifest is optional. A repository that has never been inspected behaves exactly as it did before — same prompts, same detection, same output, plus one informational line. Nothing stops, and nobody is asked to run an inspection first.

עברית · מה נשמר ומה לא

ה־manifest מכסה שבע קטגוריות: stack, commands, structure, inventory, conventions, integrations ו־auditTopics, כל אחת נשענת על מסמך מאושר מסוים.

מה שלא נשמר בכוונה: גוף ממצאי האודיט (רק האינדקס), סמכות פלטפורמה (רמזים מייעצים בלבד), מידע על סוג מכשיר (כלל לא), ומצב מחזור־חיים של משימות.

רעננות: נשמרים ה־commit וחתימה לכל מסמך. אי־עדכניות מיוחסת ברמת המסמך הבודד, כך שעריכת מסמך אחד מורידה רק את הקטגוריה שנשענת עליו. קטגוריה שלא ניתן לקבוע מדווחת כ־unknown ולא מנוחשת — כשל מוביל למצב שאינו גרוע מהמצב הקודם, ולא למצב שגוי.

התכונה שהכול נשען עליה: ה־manifest אופציונלי. מאגר שלא נסרק מעולם מתנהג בדיוק כפי שהתנהג קודם, בתוספת שורת מידע אחת. שום דבר אינו נעצר.

How information flows between commands

Each stage reads the previous stage's approved output — never a live re-derivation. Two kinds of information travel along the chain, and the distinction matters:

Decisions — copied forward

The confirmed platform, the device type, and the design reference are copied verbatim from one document to the next and never re-detected. A human confirmed them once; re-deriving them later would silently overrule that.

Observations — cited, not copied

Repository conventions, the module map and the component inventory are recorded as a path, a section anchor and a fingerprint. A later reader resolves the citation and can tell whether the source has moved since.

עברית · זרימת העבודה המלאה

שתי הפקודות הראשונות רצות פעם אחת לכל מאגר ומרועננות מדי פעם; כל השאר רצות פעם אחת לכל פיצ'ר. בכל שלב יש שער אישור אנושי, וכל שלב קורא את הפלט המאושר של השלב שלפניו — לא גזירה חיה מחדש.

שני סוגי מידע נעים בשרשרת, וההבדל ביניהם מהותי:

  • החלטות מועברות בהעתקה — הפלטפורמה המאושרת, סוג המכשיר והפניית העיצוב מועתקות מילה במילה ממסמך למסמך ואינן מזוהות מחדש. אדם אישר אותן פעם אחת.
  • תצפיות מצוטטות ואינן מועתקות — מוסכמות המאגר, מפת המודולים ומלאי הרכיבים נרשמים כנתיב, עוגן־מקטע וחתימה. קורא מאוחר יכול לפתור את הציטוט ולראות אם המקור השתנה מאז.

אם המאגר לא נסרק מעולם — דלגו על שתי הפקודות הראשונות. השאר יתנהג בדיוק כמו קודם.

07

Design principles worth keeping

Four conclusions from building this that generalise to the next plugin.

Separate observations from decisions

The useful split was not producer-versus-consumer but observations versus decisions. What a repository is can be shared. What we have decided belongs to the moment a human confirmed it. Encode that structurally — the absence of an authoritative platform field is what prevents the mistake.

Honest degradation, enforced per fact

Reporting unknown rather than guessing is what makes shared knowledge safe to trust. Stating the rule once is not enough: each derivation has to be checked against it individually. Failure must degrade to no better than before, never to wrong.

Consistency across agents is a contract problem

Where several documents carry the same fields and several components read the same summary, every inconsistency took one form: a document listing a subset of something that had since grown. Two habits fix it — point at one authoritative definition instead of restating it, and forward whole outputs instead of enumerated parts.

Optional beats required

Making the manifest optional rather than a prerequisite is why this could ship without coordinating two plugins' releases. Either can be installed alone. That constraint shaped the reader's design: it always succeeds, so no caller can mistake a missing manifest for an error.

עברית · עקרונות עיצוב
  • הפרדת תצפיות מהחלטות — לא יצרן מול צרכן. מה שהמאגר הוא ניתן לשיתוף; מה שהוחלט שייך לרגע האישור האנושי. כדאי לקבע זאת במבנה עצמו.
  • הידרדרות כשלית כנה, ברמת העובדה הבודדת — דיווח unknown במקום ניחוש הוא מה שמאפשר לסמוך על ידע משותף. אמירת הכלל פעם אחת אינה מספיקה; יש לבדוק כל גזירה מולו בנפרד.
  • עקביות בין סוכנים היא בעיית חוזה — כל אי־התאמה שנמצאה הייתה מסמך שמפרט תת־קבוצה של משהו שגדל מאז. שני הרגלים פותרים זאת: להפנות להגדרה אחת מחייבת במקום לחזור עליה, ולהעביר פלט שלם במקום חלקים מנויים.
  • אופציונלי עדיף על נדרש — העובדה שה־manifest אופציונלי היא מה שאיפשר לשחרר בלי לתאם גרסאות בין שני פלאגינים.

If you are extending the ecosystem

To add a consumer: read the contract, then note its two hardest obligations — parse the manifest in exactly one component, and never let it fail a command. מסמך זה הוא נקודת הכניסה, וכל השאר תומך בו ואינו חוזר עליו. כל תיעוד הארכיטקטורה מרוכז במאגר ה־marketplace; במאגר של כל פלאגין נשאר רק ה־README והתיעוד הדרוש לבנייה ולתרומה:

  • חוזה ה־Repository Knowledge — הסכימה המדויקת, ההתחייבויות של היצרן והחובות של הצרכן. חובה לקרוא לפני כתיבת צרכן חדש.
  • ארכיטקטורת ה־Inspector — כיצד הפלאגין בנוי: תזמור מונחה־רגיסטרי, סוגי מיומנויות, שערי אישור, hooks, סקריפטים דטרמיניסטיים, מצב והמשכה.
  • זרימת הסריקה — מה להקליד ובאיזה סדר, ומה עושה כל אחת מחמש הפקודות.
  • מפרט ההכללה — מדוע זה בנוי כך: הסקירה המלאה, הכפילויות שנמצאו, מודל הבעלות והחלופות שנשקלו ונדחו.
  • תוכנית המימוש — מה נבנה בפועל, משימה אחר משימה, כולל פקודות אימות.

להוספת צרכן חדש: קראו את החוזה, ושימו לב לשתי החובות הקשות — לנתח את ה־manifest ברכיב אחד בלבד, ולעולם לא לאפשר לו להכשיל פקודה.
